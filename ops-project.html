Ops Infrastructure Kickoff

2-3 classes, whole class, first thing this year.

Before we pitch or build anything of our own, the whole class is going to deploy a real, open-source chat app called Rocket.Chat, twice: once on your own laptop, then once for real, together, on a machine that stays on. This isn't a simulation of production software. It's the real thing, just small enough to fit in a few classes.

Why this comes first

You've written a lot of Java over the last two years, but almost none of it involved actually running software somewhere other people can use it. This course isn't about devops, but devops is inevitably part of the world your own project will live in by the end of the year. The point here is calibration: real, hands-on exposure to what deploying software involves (servers, databases, containers) before you scope your own idea, so you don't underestimate that part of the work later.

How it goes

Class 1: deploy it yourself

Every student installs Rocket.Chat on their own laptop, using its official setup. All of us at once. You'll hit small, real problems. Afterward, we talk through what you just built as a class.

Homework: draw it

Based on what you just deployed: draw an architecture diagram of the components involved. Use the Mermaid live editor to make the diagram. Also make at least two sequence diagrams for named scenarios: a login flow, and one message sent and received. These are diagramming skills you'll reuse for your own project's architecture decisions later this year.

Class 2 (likely extends into Class 3): deploy it for real, together

The class will set up the same app on a shared Mac (in Gates 212) that stays on and reachable, rather than living on one laptop. Two students should volunteer to install Uptime Kuma, a lightweight monitoring system, separately from Rocket.Chat. Once both are working, we'll connect them so Kuma can tell us if Rocket.Chat is down. While this work is ongoing, I'll have quick individual chats with everyone about your understanding of the system and process.

The diagrams

An architecture diagram shows the components and how they relate: things like a user-facing website, a server, an API, a database, or other pieces. You draw lines connecting the components that interact, and just as importantly, you should know which components do not interact. This article discusses architecture diagrams in more depth than we need today.

SSH access to the shared machine

What is SSH

Once we get to the collaborative deploy, you'll need SSH access to the Mac. This SSH setup guide will help you generate a key pair on your own laptop, send Mr. Meyer your public key, and he adds it to the shared machine so you can connect directly.

What you're actually here to learn

  1. Reading and operating a real codebase you didn't write. A real install guide, real configuration, a real database dependency. Being able to say specifically how that's different from two years of CS and Data Structures & Algorithms is the whole point.
  2. The vocabulary connects to something you actually did. Server, client, frontend, backend, API, database. By the end, these aren't new words; they're names for things you already ran into.
  3. Deployment friction is real and worth planning for. Whatever goes wrong here is a preview of what can go wrong at the end of your own capstone project.

AI use on this project

Different shape than your capstone AI policy, because the risk here is different. On your own project, the worry is "AI wrote code you don't understand." Here, you're barely writing original code; you're deploying and configuring someone else's. The real trap is subtler: asking AI to explain an error and pasting in the fix without understanding why it worked.

Use AI freely, out in the open, for

Explaining unfamiliar error messages, translating a cryptic configuration option. This is how working engineers actually use these tools; there's no reason to pretend otherwise.

Use AI to help, but explain what you shipped

Any AI-suggested change to a docker-compose file or configuration should be understood line by line before you apply it. If you can't explain why a line is there, don't ship it yet.

No AI, by design

The 1:1 conversation about your diagram is closed-book: no notes, no AI. That's the one moment this project is actually trying to check: can you explain what you built, in your own words.
