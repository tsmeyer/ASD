Ops Infrastructure Kickoff

2-3 classes, whole class, first thing this year.

Before we pitch or build anything of our own, the whole class is going to deploy a real, open-source chat app — Rocket.Chat — twice: once on your own laptop, then once for real, together, on a machine that stays on. This isn't a simulation of production software. It's the real thing, just small enough to fit in a few classes.

Why this comes first

You've written a lot of Java over the last two years, but almost none of it involved actually running software somewhere other people can use it. This course isn't about devops, but devops is inevitably part of the world your own project will live in by the end of the year. The point here is calibration: real, hands-on exposure to what deploying software involves — servers, databases, containers — before you scope your own idea, so you don't underestimate that part of the work later.

How it goes

Class 1 — deploy it yourself

Every student installs Rocket.Chat on their own laptop, using its official setup. All of us at once — no waiting in line. You'll hit small, real problems. Afterward, we talk through what you just built as a class.

Homework — draw it

Based on what you just deployed: an architecture diagram (browser → frontend → backend → database), plus one or two Mermaid sequence diagrams for named scenarios — a login flow, and one message sent and received. Same diagramming skill you'll reuse for your own project's architecture decisions later this year.

Class 2 (often bleeding into Class 3) — deploy it for real, together

The class sets up the same app on a shared Mac Mini that stays on and reachable, rather than living on one laptop. Two students peel off to add Uptime Kuma, a lightweight monitor, once the main service is live. While that pair works, everyone else gets a quick 1:1 conversation about their diagram.

Expect this to take 3 classes, not 2 — and treat that as a feature, not a slip. Nothing about a first deployment goes right the first time; that's real, and it's worth naming out loud when it happens. It's a preview of exactly the kind of thing that eats time at the end of your own project if you don't plan for it.

SSH access to the shared machine

Once we get to the collaborative deploy, you'll need SSH access to the Mac Mini. See the separate SSH setup guide for exact steps — you generate a key pair on your own laptop, send Mr. Meyer your public key, and he adds it to the shared machine so you can connect directly.

What you're actually here to learn

  1. Reading and operating a real codebase you didn't write. A real install guide, real configuration, a real database dependency — and being able to say specifically how that's different from two years of CS and Data Structures & Algorithms.
  2. The vocabulary connects to something you actually did. Server, client, frontend, backend, API, database — by the end, these aren't new words, they're names for things you already ran into.
  3. Deployment friction is real and worth planning for. Whatever goes wrong here is a preview of what can go wrong at the end of your own capstone project.

AI use on this project

Different shape than your capstone AI policy, because the risk here is different. On your own project, the worry is "AI wrote code you don't understand." Here, you're barely writing original code — you're deploying and configuring someone else's — so the real trap is subtler: asking AI to explain an error and pasting in the fix without understanding why it worked.

Use AI freely, out in the open, for

Explaining unfamiliar error messages, summarizing documentation, translating a cryptic config option. This is how working engineers actually use these tools — no reason to pretend otherwise.

Use AI to help, but explain what you shipped

Any AI-suggested change to a docker-compose file or config should be understood line by line before you apply it. If you can't explain why a line is there, don't ship it yet.

No AI, by design

The 1:1 conversation about your diagram is closed-book — no notes, no AI. That's the one moment this project is actually trying to check: can you explain what you built, in your own words.
